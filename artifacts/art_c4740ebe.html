SAP Datasphere ↔ Azure Databricks
Integration Architecture

SAP Solution Architecture Advisory 📅 October 2026 🔍 Research-Based ✅ SAP BDC + Delta Sharing
📋 Executive Summary

SAP Datasphere and Azure Databricks can be integrated through three mature patterns, each suited to different use cases. The SAP-recommended path is the SAP Business Data Cloud (BDC) Connector for Databricks, which leverages the open-source Delta Sharing / OpenSharing protocol to deliver live, zero-copy, bi-directional data access between SAP's curated data products and Databricks workspaces — without replicating or moving data.

This approach is natively integrated into Databricks' Unity Catalog, provides automatic sync of SAP semantic metadata (table/column comments, primary/foreign keys, governance tags), and uses mutual TLS + OIDC for secure exchange. For teams requiring direct extraction from SAP ERP systems, the Databricks connector ecosystem (OData, SLT, Fabric Dataflows) offers viable alternatives at the cost of added operational complexity.

This document details all three options, with a deep dive into the BDC Connector architecture, pros/cons analysis, security posture, and step-by-step implementation guidance.

🏗️ Recommended Architecture: SAP BDC Connector (OpenSharing / Delta Sharing)

SAP Business Data Cloud (BDC) is SAP's integrated data platform that bundles SAP Datasphere, SAP Analytics Cloud, and — crucially — the SAP BDC Connector for Databricks. This connector uses Databricks OpenSharing (the open-protocol implementation of Delta Sharing) to share data products defined in SAP Datasphere directly into Databricks workspaces registered with Unity Catalog. Data remains in place inside SAP's HANA Cloud storage — no ETL pipeline, no data duplication.

🚀 SAP Official Recommendation (as of 2026): Use the SAP BDC Connector for Databricks via OpenSharing for all net-new Datasphere → Databricks integration work. This is the only pattern where SAP's governance, semantic layer, and data lineage fully travel with the data.

Integration Flow
  1. Source Data Ingestion: SAP S/4HANA / ECC pushes operational data into SAP Datasphere using ODP extractors, CDS View replication, or SAP Landscape Transformation (SLT). Data lands in SAP HANA Cloud columnar storage.
  2. Data Modeling & Curation: Data engineers in Datasphere's Data Builder create Views, Data Flows, and Analytic Models. These are promoted as governed Data Products in the Datasphere catalog, ready for sharing.
  3. OpenSharing Setup (Provider Side — SAP BDC Admin): The SAP BDC admin enables OpenSharing on the Datasphere tenant and configures a Third-Party Connection. The SAP BDC admin receives a Connection Identifier from the Databricks workspace admin.
  4. OpenSharing Setup (Recipient Side — Databricks Admin): The Databricks workspace admin (with CREATE PROVIDER and CREATE RECIPIENT privileges) obtains a connection identifier and sends it to the SAP BDC admin. Once the SAP BDC admin creates the connection and returns an invitation link, the Databricks admin completes the SAP BDC connection in Unity Catalog.
  5. Data Product Sharing: The SAP BDC admin grants the Databricks recipient access to selected OpenSharing shares containing published Data Products (tables and views).
  6. Catalog Mount in Databricks: The Databricks admin creates a Unity Catalog catalog from the received share. SAP semantic metadata (column descriptions, primary/foreign keys, SAP governance tags) synchronizes automatically into Unity Catalog.
  7. Analytics & ML Consumption: Databricks users query SAP data directly via Spark SQL, Databricks SQL, or MLflow notebooks — live, without data movement. Queries resolve against SAP HANA Cloud via the Delta Sharing protocol over HTTPS/mTLS.
  8. Bi-directional Write-back (Optional): Databricks-side Delta Tables and ML outputs can be shared back into SAP Datasphere via the same connector for closed-loop scenarios (e.g., ML predictions surfaced in SAP Analytics Cloud).

🔀 Alternative Integration Options
Option 2 — SAP Connector / OData API (S/4HANA Direct → Databricks) Alternative

Databricks provides native connectivity to SAP source systems (S/4HANA, ECC, BW) through the SAP OData connector and community-maintained ODP/RFC connectors. This approach bypasses Datasphere entirely and pulls raw data directly into Databricks Delta tables via Spark.

  • Use case: Teams already on Databricks who want SAP transactional data without a Datasphere license, or needing full historical loads from BW InfoProviders.
  • Mechanism: Databricks cluster calls SAP OData services (via SAP Gateway) or uses the SAP JCo RFC library. Data lands in ADLS as Delta tables.
  • Limitations: No SAP semantic metadata, no governed data products, requires SAP Gateway setup, limited incremental extraction support without SLT or ODP configuration.
  • Microsoft tooling: Azure Data Factory's SAP ECC / SAP HANA connectors can mediate the extraction, then land data in ADLS for Databricks consumption — adding a managed ETL layer.
⚠️ This pattern does NOT leverage Datasphere's governance or semantic layer. Consider it only when Datasphere is not part of the landscape.
Option 3 — Azure Data Factory / Synapse Pipelines (ADF-mediated ETL) Alternative

Azure Data Factory (ADF) or Synapse Pipelines can act as the integration middleware between SAP Datasphere (or SAP HANA Cloud) and Azure Databricks. ADF exposes native connectors for SAP HANA, SAP OData, SAP BW and can write outputs directly to ADLS Gen2, which Databricks accesses via external tables or Auto Loader.

  • Use case: Organizations already heavily invested in Azure integration services (ADF/Synapse), or requiring scheduled batch ETL with complex transformation logic managed in Azure.
  • Mechanism: ADF pipeline reads from Datasphere OData API or SAP HANA Cloud via JDBC → transforms in ADF mapping data flows or Azure Databricks activity → writes Parquet/Delta to ADLS.
  • Limitations: Introduces data copies (ETL = data duplication), latency, and additional cost. No live/streaming access. ADF pipelines need maintenance as SAP schemas evolve.
  • Governance: Data lineage must be managed separately in Azure Purview; SAP Datasphere lineage does not propagate through ADF into Databricks.

🔒 Security & Governance Considerations
Authentication & Transport Security (BDC Connector)
  • Mutual TLS (mTLS): All data exchange between SAP BDC and Databricks is encrypted and authenticated using mutual TLS — both parties present certificates, preventing man-in-the-middle attacks.
  • OpenID Connect (OIDC): Identity federation uses OIDC tokens, enabling seamless SSO with Azure Active Directory / Microsoft Entra ID. No static passwords or API keys are exchanged.
  • Zero-copy by design: Because data never leaves SAP HANA Cloud, data residency and sovereignty requirements (GDPR, PDPA, etc.) are significantly easier to maintain.
Authorization & Access Control
  • SAP Datasphere Space Security: Data is exposed only from explicitly shared spaces; space-level access controls in Datasphere restrict which Data Products can be shared via the BDC Connector.
  • Databricks Unity Catalog Policies: Once mounted, SAP-shared catalogs inherit Unity Catalog's row-level, column-level, and table-level access control policies. Column masking and dynamic data masking can be applied on the Databricks side.
  • SAP BDC Admin Required: A dedicated SAP BDC administrator account is needed to create and manage Third-Party Connections — follow the principle of least privilege.
  • Databricks Workspace Admin Privileges: The Databricks admin performing setup must have CREATE PROVIDER and CREATE RECIPIENT privileges on the Unity Catalog metastore.
Data Governance & Lineage
  • Semantic metadata sync: Table and column descriptions, primary keys, foreign keys, and SAP governance tags auto-sync from SAP BDC Data Products into Unity Catalog — making SAP data discoverable and annotated in Databricks Catalog Explorer without manual effort.
  • SAP Data Lineage: Datasphere's built-in lineage graph tracks data from source (S/4HANA) through transformation layers to the published Data Product; this lineage is visible in the SAP Datasphere catalog.
  • Audit Trail: Both SAP BDC and Databricks maintain audit logs of all sharing events. The Databricks audit log records all share access events per recipient, supporting SOC 2 and compliance reviews.
  • Usage Disclosure: Note that Databricks may share usage telemetry (volume of SAP BDC data queried, workload timestamps, organizational pricing data) with SAP for billing and administrative purposes when using the SAP BDC Connector. Review the Databricks Privacy Notice before deployment.
Network & Perimeter
  • Ensure SAP BTP outbound network rules allow HTTPS (port 443) to the Databricks OpenSharing endpoint.
  • For private networking, Databricks supports Azure Private Link; confirm SAP BTP Private Link Service is configured if your Datasphere tenant is on Azure BTP.
  • Review and whitelist Databricks workspace IP ranges in SAP BTP network policies if IP allowlisting is enforced.
🚀 Implementation Guidance
Prerequisites
  • ✅ SAP Business Data Cloud (BDC) license — required for the BDC Connector; SAP Datasphere standalone tenants may need the BDC add-on. Confirm with your SAP Account Executive.
  • ✅ Databricks workspace on Azure with Unity Catalog enabled (Premium tier or higher).
  • ✅ OpenSharing enabled in your Databricks account — requires Account Admin setup via the Databricks Account Console (Data Sharing → OpenSharing).
  • ✅ Databricks admin with CREATE PROVIDER + CREATE RECIPIENT metastore-level privileges.
  • ✅ SAP BDC Admin role with permissions to create Third-Party Connections in SAP BDC.
  • ✅ SAP Datasphere Data Products published in at least one space — data must be modeled and released before it can be shared.
  • ✅ Network connectivity: SAP BTP → Azure (HTTPS 443); check if BTP Private Link Service is needed.
Key Configuration Steps
  1. Enable OpenSharing (Databricks Account Admin): Navigate to the Databricks Account Console → Data Sharing → enable OpenSharing for your Azure workspace. This activates the OpenSharing endpoint URL for your account.
  2. Obtain Connection Identifier (Databricks Workspace Admin): In the Unity Catalog, run SHOW PROVIDERS or navigate to Data Sharing → Providers. Obtain the connection identifier string (an encoded token) to share with the SAP BDC admin.
  3. Create Third-Party Connection in SAP BDC (SAP Admin): In SAP BDC, navigate to Administration → Connections → Third-Party Connections → New Connection of type "Databricks". Paste the Databricks connection identifier. SAP BDC generates an invitation link.
  4. Complete Connection in Databricks (Databricks Admin): Use the invitation link from the SAP BDC admin. In the Unity Catalog provider configuration, click Finish Setup with the invitation link. The SAP BDC connection will appear under Providers as active.
  5. Grant Access to SAP Data Products (SAP Admin): In SAP BDC, navigate to the published Data Products you want to share. Use Share → Grant to Recipient → Databricks. Select the tables/views to include in the share.
  6. Create a Catalog from Share (Databricks Admin): In Unity Catalog, run: CREATE CATALOG sap_bdc_data USING SHARE `<provider-name>`.`<share-name>`; SAP semantic metadata (table descriptions, keys, tags) will auto-populate into the new catalog.
  7. Validate & Test: Run a Databricks SQL query against the newly mounted SAP catalog. Verify column metadata, primary/foreign key annotations, and row counts match expectations in Datasphere. Check audit logs on both sides.
  8. Configure Row/Column Security (Databricks Admin): Apply Unity Catalog row filters and column masks as needed. Assign catalog-level GRANT permissions to Databricks users and groups.
Common Pitfalls & How to Avoid Them
  • ❌ Pitfall: Data Products not yet published. Data must be explicitly published/released in the Datasphere Data Product catalog before they appear as shareable. Unpublished views will not show up in the BDC sharing workflow. Fix: Ensure the DW Modeler has completed the Data Product release lifecycle in Datasphere.
  • ❌ Pitfall: Unity Catalog not enabled on Databricks workspace. The SAP BDC Connector requires Unity Catalog (not the legacy Hive metastore). Workspaces on the Standard tier may not support UC. Fix: Upgrade to Premium and assign the workspace to a Unity Catalog metastore before starting setup.
  • ❌ Pitfall: OpenSharing endpoint not enabled. The connection identifier cannot be generated if OpenSharing is not activated at the Databricks Account level. Fix: Account Admin must enable OpenSharing in Databricks Account Console first.
  • ❌ Pitfall: Firewall blocking BTP → Databricks HTTPS traffic. SAP BTP outbound rules or Azure NSGs blocking port 443 will silently fail the connection handshake. Fix: Whitelist Databricks OpenSharing endpoint IPs in SAP BTP network policies and Azure NSG rules.
  • ❌ Pitfall: Assuming Delta file format from Databricks is needed. OpenSharing uses the Delta Sharing protocol but data physically stays in SAP HANA Cloud columnar format — Databricks does not write Delta files for incoming SAP shares. Only Databricks-native output tables are in Delta format. Fix: Educate the team on zero-copy semantics; monitor query pushdown performance via Databricks query profiler.
  • ❌ Pitfall: Neglecting the SAP usage telemetry clause. Databricks contractually shares usage metadata with SAP (workload volumes, timing, org pricing). This must be disclosed to your legal and compliance teams before go-live. Fix: Review the Databricks Privacy Notice and SAP BDC Connector terms with your DPO before production deployment.
